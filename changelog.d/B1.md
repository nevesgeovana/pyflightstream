## Added

- `pyfs-matrix restore <kind>` brings `runs.json`, `storage_management.json`, `additional.json`, `post/<matrix>/products.json` or `post/<matrix>/plan.json` back from the workspace's archive, byte for byte: a preview by default, `--apply` to write, the current file archived first so a restore can be undone, `--stamp` and `--matrix` to choose the copy, written under the `runs.json` lease a sync holds and refused while one writes (FR-210; [Restore and rebuild the run records](docs/restore-and-rebuild.md)).
- `pyfs-matrix rebuild` makes run records again from the folders under `sims/`: each row runs again in a throwaway copy with nothing submitted, the record is rebuilt only when the executed script is the one this version renders, and the collect stage completes it read-only, so a truncated or missing output is `FAILED_INCOMPLETE_OUTPUT` and never `CONVERGED`; every rebuilt record carries a `REBUILT` warning (FR-211).
- The run layer's executor choice, build binding, per-row versions, manifest lease and read-only collection are public in `pyflightstream.run.records`: `campaign_executor`, `bind_row_builds`, `row_versions`, `manifest_lock` and `collect_without_writing` (FR-211).
- `rebuild --out NAME` writes the rebuilt records to another file and never touches `runs.json`; `runs.json` or an existing file as the name is refused before any work (FR-212).
- `rebuild --all-sims` rebuilds every simulation folder on disk, recorded or not, for comparison with `runs.json`, and requires `--out` (FR-213).
- A row switched off after it ran (`RUN 0`) still rebuilds, with `RUN 1` in the throwaway copy only and a note in the record (FR-214).
- `rebuild --build-alias BUILD=ALIAS` names the scheduler's word for a build the submission profile no longer maps, the build itself by default, in the job descriptor only; the record says which alias was assumed (FR-215).
- A POL no current matrix holds is named as waiting for the revision that ran, and `rebuild --matrix <file>` rebuilds it (FR-216).
- A run executed on a cluster and rebuilt on Windows is compared with the separators normalised and each root set aside, and its record keeps the run's own root and path style (FR-217).
- A `SUBMITTED` record is pointed to `pyfs-matrix collect` rather than given an end; with `--all-sims` each simulation takes the status its outputs support, and a folder written in the last 30 minutes stays `SUBMITTED` (FR-218).
- A drifted script is refused naming each changed line, its class (VTK export line, loads frame line, plot type line, renamed pproc group) and the input it comes from; `rebuild --inputs-from <folder>` accepts another origin's `inputs/`, and each record names the inputs taken from there, never overwriting the workspace's (FR-219).

## Migration

- A lost or overwritten `runs.json` has two ways back, and they are kept apart: `pyfs-matrix restore runs --apply` puts back an archived copy exactly, and `pyfs-matrix rebuild --apply` makes records again from `sims/` only where no archive holds them, each marked `REBUILT`. Never run `pyfs-matrix run --resume` on a simulation a rebuild refused: with no record the resume runs it again (FR-210, FR-211).
