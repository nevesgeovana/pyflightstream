# Erratum: CMP-26123_2026-08-17_full-sim carries no date in its body

**This is a REPORT-LEVEL erratum**, and it is the first of its kind here.
Every previous erratum in this directory corrects one RECORD of a report,
which is what the contract in `README.md` was written for. This one
corrects a field belonging to no record, so the contract was extended in
the same commit rather than stretched silently; that extension is marked
below as owed to the author.

**It corrects no verdict.** All 85 judgments in the report stand exactly
as the probe harness wrote them. What is wrong is one metadata field and
the rendered header derived from it.

## The sentence that is wrong

`CMP-26123_2026-08-17_full-sim.yaml` line 3:

    date: null

and, derived from the same value, the first line of its Markdown twin:

    # Compat report: FlightStream 26.123 (None)

**The date is 2026-08-17.** It is in the report's own file name, it is
the date of the commit that added it, and it is the date of the licensed
session recorded in the run sheet.

## Why it is wrong, and it is not a hand edit

The report was written by `pyfs-qa probe` on 2026-08-17, and
`write_compat_report` cannot emit a null date as the function stands
today: it resolves `date = date or datetime.date.today().isoformat()`
before building the document.

It could on the day. The refusal on an existing report was being moved
ahead of the solver in the same session, and `compat_report_paths` was
split out of `write_compat_report` to make that possible. In the
uncommitted intermediate state the date defaulting had moved INTO the new
helper and had not yet been restored beside it, so the STEM got a date
and the BODY did not. The probe run landed in that window.

That is established rather than inferred. Deleting exactly one line from
the current `write_compat_report` and re-emitting the run reproduces both
committed files BYTE FOR BYTE, which also rules out a hand edit, since a
hand edit would have to reproduce `yaml.safe_dump`'s output and the
Markdown renderer's exact bytes. The reproduction is
`INC-20260817-2210-pyflightstream` in the shared incident ledger.

## What it costs while it stands

`Judgment.date` reads a missing date as the empty string and
`contradicting_evidence` orders supersession on it, so the empty string
sorts oldest. Every one of the 85 rows citing this report is therefore
superseded by any dated 26.123 report, INCLUDING one older than it. The
effect today is nil, because the only other 26.123 report judges nothing
promotably, and it is a live trap for the next one.

## What changed so no future report repeats it

Two guards, both added on 2026-08-17 and both proven by mutation rather
than by passing:

* `tests/test_command_db.py::test_every_compat_report_carries_the_date_its_own_name_claims`
  walks every committed compat report and requires the body date to be
  present and equal to the date in the stem, and the Markdown header to
  carry it. This file is its single named exemption, which is why this
  erratum has to exist for the suite to pass.
* `tests/test_qa_compat.py::test_the_writer_stamps_one_date_in_the_stem_the_body_and_the_header`
  calls the writer with NO date argument, which no previous test did, and
  requires the three copies to agree. Its second arm requires
  `compat_report_paths` to default the same way, because the mirror-image
  mutation (the default surviving in the writer and lost from the helper)
  corrupts the pre-flight refusal instead, which is the collision check
  that exists to stop a licensed run being discarded.

## What is NOT done here, and it is the author's call

The 85 database rows still cite an undated report. Repairing that means
re-emitting the same run through the sanctioned writer under a new label
so the rows can be re-pointed by `pyfs-qa apply-compat`, and that creates
a SECOND committed report of ONE licensed run, which no rule here
contemplates. Measured on a copied tree rather than argued: the
re-emission re-points all 85 rows and the old report raises no
contradiction, because an empty date never supersedes and the outcomes
agree in any case.

Two options, with what is wrong with each:

1. **Leave it, as it is left today.** The evidence is intact, the
   citations point at a real report, and this erratum carries the date a
   reader needs. The ordering inversion stays until a second 26.123
   report exists.
2. **Re-emit under a new label and re-point the rows.** The citations
   then name dated evidence. Two reports of one run exist forever, the
   undated one keeps its permanent exemption above, and the re-emitted
   file is a DERIVATION rather than the measurement: its `executor` line
   would have to be pinned from this file rather than recomputed, or it
   would silently describe the machine that re-emitted it.

Nothing here forecloses either. The lane may not edit a committed
compatibility report, so it did neither.

## Owed to the author, marked rather than taken

`README.md` in this directory says an erratum "names the RECORD it
corrects, not the whole report". This erratum names no record, because
the defect belongs to none. The README gained a paragraph admitting a
report-level erratum in the same commit; whether that is the right
extension of the contract, and which of the two options above to take,
are both hers.
