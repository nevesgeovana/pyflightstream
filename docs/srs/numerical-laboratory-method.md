# Numerical laboratory method

pyflightstream formalizes FlightStream as a numerical laboratory: a numerical experiment is designed as a protocol, carried out as a procedure on the instrument, recorded, reduced and assessed with the rigor and provenance required to trust a simulation result. The method below states the requirements that any such driver meets, independent of the solver; the FlightStream requirements instantiate them through `Derives from`.

## Simulation as experiment

Wind-tunnel practice earned the trust of the aeronautical community through a small number of habits: the instrument is calibrated and the certificate is kept; the test matrix is written before the occupancy; the test article is inspected; the run log records every run, good or aborted; the data are reduced by published equations with tares and corrections labelled; repeat runs, check standards and an uncertainty budget come before any coefficient is believed; and the whole test is filed under one number. A numerical experiment deserves the same habits, and a solver driver can enforce most of them; where a habit changes meaning for a deterministic solver, as the repeat run does, the [trust stage](#trst-establish-trust) says so. This page states that method as requirements. Each stage of the laboratory is one goal (L0) refined by a small set of central requirements (L1), and each central requirement names the experimental practice that motivates it.

| Stage | Name | Experimental counterpart | What the stage guarantees |
| --- | --- | --- | --- |
| INST | Know the instrument | The calibration certificate of the tunnel and the balance | every build is an identified instrument whose operations carry evidence |
| DEXP | Design the experiment | The test matrix and the test plan, written before the occupancy | the protocol is resolved and checked before anything runs |
| SPCM | Prepare the specimen | The test article and the model inspection report | specimens are identified, unmodified at source, accepted and replayable |
| PHYS | Configure the physics | The configuration sheet: conditions, references, axes, signs | one explicit model configuration per case, admitted by the instrument |
| PROC | Translate to the instrument | The run card derived from the plan and checked against facility limits | identical inputs give an identical, validated procedure |
| EXEC | Run the experiment | The occupancy and the run log | authorized, bounded runs with an explicit outcome per case |
| RECS | Record the experiment | The laboratory notebook and the data-acquisition header | a record that audits, attributes and reconstructs each run |
| DRED | Reduce the data | Data reduction, tares and corrections | products by definition of record, with condition, domain and provenance |
| TRST | Establish trust | Uncertainty budget, repeat runs, check standards | evidence, controls, references and limits behind every claim |
| WKSP | Keep the laboratory | The test archive | one reviewable, recoverable, portable workspace |
| OPER | Operate and learn | The operating manual and the control-room console | documented interfaces whose behaviour matches the release |

## Two layers, and the theory layer they cite

The specification has two layers. The **method layer** is this page: eleven goals and the central requirements of the numerical laboratory, stated for any numerical solver driven as an instrument. The **instantiation layer** is the pyflightstream requirement set, where each feature derives from the central requirements it realizes and is refined down to the behaviour a test verifies. Neither layer states physics. Every formula, window, token, axis convention and validity range lives in the **theory layer**: [the post-processing definitions](../post-processing-definitions.md) and the definitions pages under `docs/definitions/`. A requirement cites a definition and never restates a formula; where a definition and the code disagree, the definition is right.

Solver independence is deliberate: no statement below names a solver, a programming language, a file format or a discipline-specific device. The aerodynamic vocabulary lives in the analogy column and in the theory layer, so that the method claims transfer to another solver while the instantiation stays concrete. The wording admits both readings: a method for numerical solvers in general, and a method for aerodynamic solvers in particular.

## Protocol and procedure

The protocol is the design of a numerical experiment, decided and recorded before any run: what is tested, under which conditions, with which variables and controls, and what is measured. In pyflightstream it is the run matrix, the setup standard and the post-processing declaration (stage DEXP).

The procedure is the sequence of operations on the instrument that carries the protocol out: the generated solver script and the plan, run and collect steps (stages PROC and EXEC). The researcher writes the protocol and never the procedure; the library derives and checks the procedure from the protocol, so two engineers with the same protocol obtain the same procedure.

## How to read a requirement

Every row carries seven cells. **UID** is permanent: `NL-<STAGE>` for a goal and `NL-<STAGE>-<n>` for a central requirement; a retired UID is listed below and never reused. **Level** is L0 (goal) or L1 (central requirement). **Statement** is one sentence with one *shall*; the subject *the system* means the numerical laboratory driver, the software that drives the instrument, of which pyflightstream is one instance. **Rationale** says why the guarantee exists and cites the theory layer where physics is involved. **Analogy** names the wind-tunnel practice the requirement transfers. **Verification** starts with one of *test*, *analysis*, *inspection* or *demonstration* and states the acceptance procedure. **Source** lists the standards and literature the requirement rests on, by the locators of the [sources](#sources) section.

Statements follow the writing rules of the specification: an approved subject, active voice, no vague or open-ended terms, no bare pronouns, no implementation vocabulary, at most forty words. Conditional behaviour uses the EARS patterns. A goal is verified by analysis: the goal holds when every central requirement under the goal is verified. A central requirement whose verifying evidence does not exist yet is listed in the [verification owed](#verification-owed) section until the evidence exists.

Three words carry two meanings in the communities this page addresses, and the page holds each to one sense. **Verification** in the Verification column is the requirements sense (ISO/IEC/IEEE 29148 [REF-23]): evidence that the system meets the requirement. The code and solution verification of stage TRST is the computational sense (AIAA G-077 2.2 [REF-24]): evidence that the equations are solved correctly. **Validation** is used only in the computational sense: agreement of the model with measured data for an intended use. **Calibration** follows test-section and balance calibration (VIM 2.39 [REF-60]): a calibration study characterizes a setting of the instrument, such as panel density or time step, against error and cost. It never adjusts model parameters until results match measured data; the V&V literature calls that model calibration and keeps it apart from validation (AIAA G-077 4.2 [REF-24]).

One software term recurs because the records depend on it. A **digest**, or content hash, is a short fingerprint computed from the bytes of a file: identical bytes give an identical digest and any change gives a different one, so a record that cites a digest names exactly one content, as a serial number names one balance. Every digest is a sha256 of the canonical form that `pyflightstream._digest` defines for its kind.

## Central requirements (L1)

### INST Know the instrument

A wind-tunnel engineer does not trust a balance because the balance is bolted in; the engineer trusts the calibration certificate that names the balance, the loads applied and the date. The instrument stage asks the same of a solver: every build is an identified instrument, every operation of that build is backed by a citation or by a committed measurement, and an operation without evidence is refused or admitted under a recorded exception.

| --- | --- | --- | --- | --- | --- | --- |
| NL-INST-1 | L1 | The system shall bind each instrument operation to a registered instrument identity that distinguishes distinct executables independently of display labels. | Identity precedes capability and result claims: two executables with one label are two instruments. ### SPCM Prepare the specimen

The test article is inspected before the test and the inspection report is part of the test file. The specimen stage asks that geometry and meshes enter the laboratory from identified, unmodified sources, under declared operations, and leave preparation only as accepted, replayable specimens. A mesh family for a refinement study is one geometry at several resolutions, as a denser pressure-tap layout is drilled into the same model so that the integrated load changes with tap density alone. A mesh family is not a family of models at several scales: a change of scale changes the Reynolds number, and with it the physics.

### PHYS Configure the physics

The configuration sheet of a run states the flow conditions, the reference quantities, the axes and the sign conventions. The physics stage resolves every modelling input of a case to one value or an explicit unknown, keeps quantities and directions intact through every mapping to the instrument, refuses configurations outside the declared rules, and exposes every instrument setting as a declared input or a recorded exclusion.

### PROC Translate to the instrument

The operator runs a card derived from the test plan, not a plan rewritten at the console. ### TRST Establish trust

No facility reports a coefficient without a check-standard run, repeat runs, an uncertainty budget and a statement of the valid envelope. The trust stage judges convergence from evidence, compares results with declared references under stated metrics, reports applicability limits, requires controls behind every claim, keeps the history of overridden verdicts, and estimates the numerical uncertainty from a refinement study.

What the stage can claim is bounded, and the bound is part of the method. Verification has two parts in the V&V literature (AIAA G-077 2.2 [REF-24]; Oberkampf and Roy ch. 2 [REF-62]): code verification asks whether the equations are solved correctly, and solution verification estimates the numerical error of one solution. The laboratory verifies its own reductions against analytical and manufactured oracles (NL-DRED-2) and estimates the iterative and discretization error of each result (NL-TRST-1, NL-TRST-7); the code verification of the solver belongs to its developer, and the laboratory adds evidence only through comparisons with analytic and committed reference cases (NL-TRST-2). A comparison with another build or with a stored band detects drift; only a comparison with measured data, with the experimental, input and numerical uncertainties accounted for, validates the model for an intended use (ASME V&V 20 [REF-61]). A deterministic solver repeats itself to within round-off, so its repeat run checks that the same inputs give the same result and estimates no scatter. The laboratory therefore supplies the numerical part of an uncertainty budget; input and model-form uncertainty need sensitivity studies and validation against measured data, which the method records and does not replace.

## How the instantiation refines the method

Each pyflightstream feature (an instantiation L1) derives from one or several central requirements, never from all of them; the derivation is recorded in the `Derives from` column of the requirement set. A feature with no central parent is either a solver particularity stated as such (the aerodynamic product catalogue under NL-DRED-2, the fluid-structure route under NL-PHYS-4) or a sign that the method misses a guarantee, and both are findings. A central requirement with no feature is reported as method scope not yet instantiated, never hidden. The quality requirements (the Q tree of ISO/IEC 25010:2023) constrain stages and features; they derive from no stage.

## Retired identifiers

A retired UID keeps its place in the numbering and is never reused. Each one names the requirement that carries its guarantee.

The method admits no aspirational requirement: a central requirement stays in the method only while the evidence that verifies it exists or is being produced. The rows below name what is still owed to the requirement; a goal holds only when nothing is owed to any of its central requirements.

| --- | --- |
