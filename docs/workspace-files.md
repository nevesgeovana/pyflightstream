# Workspace files

A workspace keeps campaign inputs, executable scripts, run evidence and derived products together. The run manifest records identity and provenance; directory names alone do not establish what ran.

The reference below is generated from the checkout's Python declarations and verified function locations. File names in angle brackets are patterns, not literal names. A row can describe a file family. Optional files appear only when the corresponding operation or export is selected. Creation timing is stated in **What it holds**.

**Limits:** this page describes documented paths and lifecycle rules; it does not inspect a live workspace.

The governing TOML, YAML, JSON and CSV files are plain text so changes to a protocol and its records can be reviewed under version control. Keep machine-local settings separate; identify bulk solver artifacts by their recorded hashes.

## Example: a small steady campaign

This illustrative tree contains one steady simulation with an alpha sweep. The first point is expanded; the other points have the same layout. The matrix and inputs must be supplied after initialization. Product and script stems depend on the naming policy and selected groups.

~~~text
steady-study/
|-- pyfs.toml                         # optional shared command defaults
|-- pyfs.local.toml                   # optional machine overrides
|-- matrix.fs                        # campaign rows, also allowed in inputs/matrices/
|-- runs.json                        # authoritative evidence after run or submission
|-- storage_management.json          # appears after a storage operation
|-- inputs/
|   |-- executables.toml             # registered solver builds
|   |-- INPUTS.md                    # generated input glossary
|   |-- input_template.md            # generated examples of input files
|   |-- geometries/
|   |   |-- README.md
|   |   \-- wing/
|   |       |-- wing.obj             # prepared mesh
|   |       \-- wing.boundaries.toml # boundary and import declarations
|   |-- references/r001.toml         # reference quantities
|   |-- setups/s001.toml             # solver settings
|   |-- pproc/
|   |   |-- p001.toml                # requested exports and products
|   |   |-- VARIABLES.md
|   |   \-- WRITING-EQUATIONS.md
|   \-- matrices/                    # optional alternative matrix home
|-- sims/
|   |-- batch/                       # only when grouped jobs are prepared
|   \-- sim_1001/
|       |-- inputs/wing.obj          # staged copy or link
|       |-- scripts/<sweep-stem>.txt # emitted commands
|       \-- datapoints/
|           |-- DP-AL+000/
|           |   |-- P1001-AL+000.txt     # collected loads
|           |   \-- P1001-AL+000_log.txt # solver log, if exported
|           |-- DP-AL+002/
|           \-- DP-AL+004/
|-- post/
|   \-- matrix/
|       |-- plan.json               # planning receipt
|       |-- campaign_sweep.csv      # sweep outcomes
|       |-- polars/<polar>.csv      # reduced engineering table
|       |-- provenance/<run>.prov.json
|       |-- products.json           # inventory and product status
|       |-- post.log
|       \-- post.log.json
|-- logs/                            # command activity, created on demand
\-- archive/                         # preserved evidence before managed changes
~~~

Initialization also creates the empty profiles, freestreams, calibrations, hpc, fsi and management input folders listed below. Optional sixdof and costs folders are supplied on demand. There is no per-simulation plan.json or separate run-record file on the traced steady route: the plan is in post/&lt;matrix&gt;/plan.json and run records are in root runs.json. Without a matrix name, the plan is at the root.

!!! warning "Never edit run evidence by hand"
    Never hand-edit runs.json, additional.json, their archived records or generated provenance records. Use the supported run, collect, marking, storage and recovery operations. Changing recorded definitions, hashes or identities can invalidate the link between a run and its evidence.

The **Written by** and **Read by** columns use module:function names. Directory writers create the container; they do not necessarily author its contents. A collector moves solver outputs into managed storage. **not found** means that a Python writer or reader was not identified in the source audit, including user-authored inputs and files written by the external solver. It does not imply that a file is unused or safe to delete. Reader lists name selected owners, not every transitive caller. Edit and delete advice is a conservative interpretation of the code paths.

Every simulation and product file links to the relevant stage in the [execution view](understanding/execution.md). Optional products link to their containing post-processing stage even when the example does not request them. The [generated data](understanding/data/workspace-files.json) includes source locations and function hashes for auditing.
